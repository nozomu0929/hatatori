# ハタトリ

CTFの**終了済み問題を復習し、解法の過程を身につける**ための学習支援ツール。

> ⚠️ 本ツールは学習・練習用です。**開催中の競技での使用は想定していません。**
> 多くのCTFは自動解析ツールによる解答や、解法の外部共有を規約で禁じています。
> 使用は、終了済みの問題・練習用問題・自分が権利を持つファイルに限定してください。

## 設計思想

フラグを出すことではなく、**なぜその手を選んだのかを説明すること**が目的。
そのため全アナライザは結果ではなく「思考の跡」を返す:

| 項目 | 内容 |
|---|---|
| 観察 | 客観的に何が見えたか |
| 根拠 | なぜそれが手がかりなのか（**教材の本体**） |
| 操作 | それを受けて何をしたか |
| 手動 | 手で解く場合の等価コマンド（技能の移転） |
| 結果 | 何が得られたか |
| 補足 | 初心者向けの背景知識 |

`command` を必ず併記するのは、ツールに依存させず `binwalk` や `xxd` を
自分で打てるようになってもらうため。

## 見た目

- テーマカラー **臙脂色 `#b94047`** ／ サブ **赤 `#e03131`**
- 地の色も無彩色ではなく僅かに赤へ寄せ、ジャンル識別色も
  無関係な色相を並べずに暖色の階調で揃えている
- 臙脂は暗いので、暗背景に文字として置く箇所だけ明るい同系色 `--accent-text` を使う

アイコンは黒地に臙脂の「CTF」＋細い白枠、下に赤のアクセント線。

```bash
npm run icons   # public/ にアイコン一式を生成
```

SVGとPNGを**同じ幾何定義から出力する**（別々に書くと必ず食い違うため）。
字形は軸に平行な矩形の集合として定義してあり、
SVGではパスに、PNGでは自前のラスタライザ（3×3スーパーサンプリング）で描く。
白枠は矩形を外側へ広げた和集合として求めている
（膨張は和集合に対して分配できるので、矩形ごとに広げてよい）。

用途で配置を変える:

| 出力 | 配置 | 理由 |
|---|---|---|
| `icon.svg` | 角丸・中央80%内 | ホーム画面用。マスカブルの安全域に収める |
| `favicon.svg` / `favicon-32.png` | 角丸なし・字を最大化・装飾なし | 16pxまで縮むため |
| `icon-192/512.png`, `apple-touch-icon.png` | 全面塗り | プラットフォーム側が独自の形で切り抜くため |

## 使い方

### Webアプリ（PWA）

```bash
npm install
npm run dev       # http://localhost:5180
npm run build     # dist/ に出力（全部込みで約64KB）
```

画面は2つ。既定は**「学ぶ」**（このアプリの目的は解析結果を得ることではなく、解けるようになること）。

### 「学ぶ」画面

スキル一覧 → 解説を読む → 練習問題を生成 → 手元で解く → 答え合わせ、という流れ。

- 問題ファイルはダウンロードして**自分のツールで解く**のが本筋
- 詰まったら「ヒントを見る」で1手ずつ開く。ヒントを出し切って初めて全解説への導線が出る
- 正解すると習得済みになり、そのスキルを前提としていた次のスキルが開放される
- 進捗は端末内（localStorage）に保存。サーバには何も送らない
- 未開放のスキルでも**解説は読める**。前提は順序の案内であって、閲覧の制限ではない

### 「解析する」画面

ファイルをドラッグ&ドロップ（モバイルはタップして選択）すると解析が始まる。
表示モードは3つ:

| モード | 内容 |
|---|---|
| **ヒント**（既定） | 手がかりを1つずつ提示。自分で次の一手を考える |
| 全解説 | 観察→根拠→操作→手動→結果 を全手順ぶん表示 |
| 構造 | 抽出されたファイルの入れ子構造 |

**答えは常に伏せてある。** 目的は答えを得ることではなく解けるようになることなので、
フラグを見るには明示的な操作を挟む設計にしている。

解析は Web Worker 上で完結し、**ファイルは一切送信されない**。
Service Worker を積んでいるのでオフラインでも動く。

### CLI

```bash
npm run samples            # 検証用サンプル問題を生成
npm run verify             # 解析エンジンの正解率を測定
npm run solve -- <file>            # 解法を全手順まるごと解説
npm run solve -- <file> --quiz     # 答えを伏せてヒントだけ段階提示
npm run solve -- <file> --flags     # 答えだけ
npm run solve -- <file> --format 'picoCTF{}'   # フラグ書式を指定
```

## 教材（スキルツリー）

学習の単位は「ツールの使い方」ではなく **「考え方」**。
binwalkの使い方を覚えてもbinwalkが無い場面で手が止まるが、
「正規の終端より後ろにデータがあるか確かめる」という考え方は形式にもツールにも依存しない。

```bash
npm run curriculum              # スキルツリーの整合性 + 全問題の検証
npm run curriculum -- --seeds 200   # 種を増やしてファジング
npm run challenge -- png-append-zip # 問題を1つ生成して challenges/ に出力
npm run challenge               # 生成器の一覧
```

### 問題は配布せず、その場で生成する

問題ファイルを用意して配る代わりに、端末上で生成する。これで4つの問題が同時に片付く:

| 課題 | 生成方式での解決 |
|---|---|
| 素材の権利処理 | 自前生成なので発生しない |
| 問題の配信 | 不要。端末内で作る |
| 答えの流出 | フラグが毎回変わるので共有が無意味 |
| 解説の作成 | 解析エンジンの walkthrough がそのまま解説になる |

種（seed）を指定すれば同じ問題が完全に再現されるので、
「昨日の問題をもう一度」も不具合の再現も種の共有だけで済む。

### 教材と実装の乖離を検出する

各生成器は「この問題を解く過程で必ず通るはずのアナライザ」を宣言している。
検証時にはフラグへの到達だけでなく、**想定した筋道を通ったか**まで確かめる。
フラグが出ても違う経路で出たなら、その問題は狙った考え方を練習させていないため。

問題は生成物なので、種を増やせばそのままファジングになる
（現在 14 生成器 × 200 種 = 2,800 ケースが全て合格）。

## 現状の対応範囲

- **recon** — マジックバイト判定 / エントロピー / strings
- **forensics** — PNGチャンク解析、CRC不一致（寸法改竄）検出、IEND以降の余剰データ、
  ZIP展開（無圧縮/deflate、暗号化検出）、埋め込みファイル走査（binwalk相当）
- **crypto** — Base64 / Base32 / 16進 / ROT-n総当たり / 単一バイトXOR総当たり
- **stego** — PNGの画素展開（フィルタ全種・グレースケール/パレット/RGBA対応）、
  LSB抽出（チャンネル・ビット順の総当たり）、ビット面の異常検出と画像化
- **rev** — ELF32/64の構造解析（ヘッダ・セクション）、.rodata/.dataの切り出し、
  コード中に1バイトずつ埋め込まれた文字列の復元
- **osint / geo** — EXIF解析（TIFF形式のIFD、JPEGのAPP1・PNGのeXIfチャンク両対応）、
  GPS座標の度分秒→十進度換算と符号の判定
- 抽出したファイルは**再帰的に**同じ解析にかけられる（多重エンコード・入れ子書庫に対応）

依存パッケージはゼロ。`Uint8Array` と Web標準API のみで書かれているため、
このコアはそのままブラウザ（PWA）でも動く。

### 収録スキル

学習可能 12 / 構想段階 3。

| Lv | スキル | 内容 |
|---|---|---|
| 0 | 読める文字を探す / ファイルの正体を見抜く | strings、マジックバイト |
| 0 | Base64を見分ける / シーザー暗号と総当たり | 符号化と暗号の区別、鍵空間を数える発想 |
| 1 | 終端の後ろを見る / メタデータを読む / Base64以外の符号 | 余剰データ、EXIF・tEXt、文字種による判別 |
| 2 | 埋め込みファイルの切り出し / アーカイブを掘り進む / 多重エンコード / XORと鍵の総当たり | カービング、再帰、総当たり |
| 3 | ファイル形式の構造を読む / 画素に埋め込まれた情報 / 実行ファイルの地図を読む | チャンク構造、LSB抽出、セクション |
| 2 | 写真に残った位置情報 | EXIFのGPSタグ |
| 3 | 座標の符号と表記 / 断片をつないで像を作る | 南緯西経の符号、複数タグの突き合わせ |
| 4 | ビット面を目で見る / 定数が符号化されている / 命令そのものを読む | 自動化の限界、難読化、逆アセンブル |
| — | 写真の写り込みから場所を絞る | 構想段階（実写素材が要るため生成できない） |

### 答えが生成物から決まる問題

座標問題では、フラグは事前に決めるのではなく **生成した画像のEXIFから計算される**。
`build` が `flag` を返して上書きできるようにしてある。

この形の問題は、丸め誤差ひとつで「正解に到達できない問題」が生まれる。
そこで生成器に `selfCheck` を持たせ、
**出題したファイルから学習者と同じ手順で答えを再計算して突き合わせる**。
エンジンが手順を出したかどうか（`expectStep`）とは別に、内容そのものの正しさを担保する。

### 生成されるバイナリは本物

rev の問題は実際のELF64を組み立てている。`file` は
`ELF 64-bit LSB executable, x86-64, statically linked, stripped` と認識し、
`readelf -S` はセクションを、`objdump -d` は x86-64 命令を正しく逆アセンブルする。
教材が「objdump -d して movb を探せ」と言い、実際にそれで解ける。

なお実行することは想定していない（そもそも素性の分からないバイナリを実行しないのが
revの作法であり、`rev-static` で最初に教える内容でもある）。

### 自動で解ける問題と、目で見るしかない問題

生成器は `solvable` で区別する。

- **auto** — エンジンがフラグ文字列まで到達できる。検証は「フラグに到達したか」で行う
- **assisted** — 最下位ビット面に文字が*絵として*描かれている類。ビットを集めても
  意味のあるバイト列にはならず、白黒画像として見て人間が読む以外に方法がない。
  検証は「人間が読むための手がかり（ビット面の画像）を必ず出したか」で行う

この区別が無いと、検証が assisted 型を「フラグ未検出＝不合格」と誤判定する。
